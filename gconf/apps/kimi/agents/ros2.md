# 代码编码与重构规范
## 命名规范：拒绝“神秘命名”
规范要求：**名字必须清晰表达意图，能一眼看出“是什么”和“为什么”**。
坏味道对应“神秘命名”：名字含义模糊，不能清晰表达功能和用法。
- **函数命名**：用动词短语，说明“做什么”。例如 `calculateTotal()` 而不是 `data()`。
- **变量命名**：用名词短语，说明“存什么”。例如 `userList` 而不是 `list1`。
- **避免编码**：不要用 `m_name`、`strName` 这种带类型前缀的命名。

## 函数设计：短小、单一职责
规范要求：**函数应该短小，且只做一件事**。
坏味道对应“过长函数”和“发散式变化”。
- **长度建议**：超过一屏（约50行）的函数就应该考虑拆分。
- **拆分手法**：使用**提炼函数**，把大段代码抽成独立函数，用函数名解释用途。
- **减少参数**：参数超过3-4个就是“过长参数列”。如果多个参数总是一起出现（“数据泥团”），用**引入参数对象**把它们封装成一个类。

## 消除重复：DRY原则的极致执行
规范要求：**任何重复的逻辑都必须被消除**。
坏味道对应“重复代码”：相同结构出现在多个地方，修改时容易遗漏。
- **同类内重复**：用**提炼函数**。
- **兄弟类间重复**：用**函数上移**把公共代码提到父类。
- **只有细微差异**：不要用 if/else 硬塞，用**多态取代条件表达式**。

## 控制流简化：卫语句与管道
规范要求：**减少嵌套层级，让正常流程线性化**。
坏味道对应“过长函数”和“循环语句”。
- **卫语句**：对于异常/边缘情况，提前 `return` 或 `continue`，不要用嵌套的 if/else 把主逻辑包起来。
- **用管道替代循环**：如果语言支持（如 Python 列表推导、Java Stream、JS 数组方法），优先用管道操作替代显式 for 循环，提高可读性。
- **拆分循环**：一个循环如果干了不止一件事，拆成多个循环，每个只做一件事。

## 消除“基本类型偏执”：为业务概念建类
规范要求：**不要用语言自带的基本类型（int, string）表达业务概念**。
坏味道对应“基本类型偏执”和“数据泥团”。
- **典型场景**：钱、坐标、范围、电话号码，不应该用 `int`、`double` 或 `string` 直接存。
- **规范**：为这些概念创建专门的类（Value Object），把相关的逻辑（如单位转换、范围判断）封装进去。
- **好处**：当需要新增一个业务逻辑时，你修改的是这个类，而不是散落在各处的“霰弹式修改”。

## 类设计：高内聚、低耦合
规范要求：**类要小而专注，拒绝“过大的类”和“中间人”**。
坏味道对应“过大的类”、“冗余类”、“中间人”。
- **单一职责**：一个类如果因为多个原因发生变化（“发散式变化”），就要**提炼类**拆分。
- **拒绝中间人**：如果一个类的接口有一半都是委托给其他类，说明它只是个“中间人”，考虑**移除中间人**或**内联类**。
- **消除消息链**：避免 `a.getB().getC().doSomething()` 这种过度耦合的调用链。用**隐藏委托关系**来缩短链路。

## 数据管理：封装可变性
规范要求：**谨慎对待可变数据，限制其影响范围**。
坏味道对应“可变数据”和“全局数据”。
- **封装变量**：不要直接暴露字段，用 getter/setter 或专门的函数控制读写。
- **拆分变量**：一个变量如果被多次赋值用于不同目的，**拆分变量**，让每个变量只承担一个职责。
- **消除临时字段**：如果类里有字段只在特定情况下才用到（“令人迷惑的暂时字段”），把它**提炼到单独的类**中。

## 注释规范：好代码不需要解释“做什么”
规范要求：**注释只解释“为什么”，不解释“做什么”**。
坏味道对应“过多的注释”：很多注释是因为代码本身不够清晰才出现的。
- **优先重构**：遇到需要写注释解释一段代码在做什么时，先尝试**提炼函数**并给它起个好名字，然后删掉注释。
- **保留注释的场景**：解释业务规则背后的原因、标注 TODO、解释非直观的算法选择。

## 删除冗余：YAGNI 原则
规范要求：**不写“将来可能用到”的代码**。
坏味道对应“夸夸其谈通用性”和“冗余类”。
- **规范**：只实现当前明确需要的功能。删除未被使用的抽象类、未被调用的函数、只为“以防万一”保留的代码。
- **手法**：**内联函数**、**内联类**、**移除死代码**。

## 持续重构的心态规范
这是全书最重要的“元规范”：
1. **重构不是项目结束后的额外工作，而是编码的一部分**。
2. **小步快跑**：每次重构只做一步，随时保持代码可运行、测试通过。
3. **发现坏味道立即处理**：不要“先堆功能，以后再说”。坏味道会累积，越晚处理成本越高。
